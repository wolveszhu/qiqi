### `connection.rs`（核心骨架，实现时全文落地）

```rust
use std::{path::Path, sync::Mutex};

use rusqlite::Connection;

use crate::error::AppError;
use super::migrations;

const KEY_SERVICE: &str = "com.brave.qiqi";
const KEY_USER: &str = "sqlcipher-key";

/// 管理态容器：`.setup()` 中 `app.manage(...)`，命令层经 `State<AppState>` 访问。
pub struct Db {
    pub conn: Mutex<Connection>,
}

/// 初始化入口：密钥 → vec 注册 → 打开 → 迁移。
pub fn init(db_path: &Path) -> Result<Db, AppError> {
    let key = load_or_create_key()?;
    register_vec_extension()?;

    if let Some(dir) = db_path.parent() {
        std::fs::create_dir_all(dir).map_err(|e| AppError::Io(e.to_string()))?;
    }
    let conn = Connection::open(db_path).map_err(AppError::from)?;
    // PRAGMA key 必须是连接上第一条语句；密钥为本地生成 hex（非用户输入），
    // 不适用参数化查询约束（rule.md §H 的参数化针对业务数据 SQL）。
    conn.execute_batch(&format!("PRAGMA key = \"x'{key}'\";"))
        .map_err(AppError::from)?;

    apply_migrations(&conn, db_path)?;
    Ok(Db { conn: Mutex::new(conn) })
}

/// 版本三分支（附录 A §A.6）：版本读取以 rusqlite_migration 为准，禁止手工覆写 user_version。
fn apply_migrations(conn: &Connection, db_path: &Path) -> Result<(), AppError> {
    let chain = migrations::chain();
    let current = chain.current_version(conn).map_err(AppError::from)?;
    let target = chain.len();

    match current.cmp(&target) {
        std::cmp::Ordering::Equal => Ok(()),
        std::cmp::Ordering::Greater => Err(AppError::Config(format!(
            "数据库版本 {current} 高于应用支持的 {target}，请升级应用"
        ))),
        std::cmp::Ordering::Less => {
            let backup = db_path.with_extension("db.bak");
            std::fs::copy(db_path, &backup).map_err(|e| AppError::Io(e.to_string()))?;
            chain.to_latest(conn).map_err(AppError::from)
        }
    }
}

/// Windows 凭据管理器取/建 32 字节 hex 密钥。
fn load_or_create_key() -> Result<String, AppError> {
    use keyring::Entry;
    let entry = Entry::new(KEY_SERVICE, KEY_USER).map_err(|e| AppError::Io(e.to_string()))?;
    match entry.get_password() {
        Ok(key) => Ok(key),
        Err(keyring::Error::NoEntry) => {
            let mut buf = [0u8; 32];
            getrandom::getrandom(&mut buf).map_err(|e| AppError::Io(e.to_string()))?;
            let key: String = buf.iter().map(|b| format!("{b:02X}")).collect();
            entry.set_password(&key).map_err(|e| AppError::Io(e.to_string()))?;
            Ok(key)
        }
        Err(e) => Err(AppError::Io(e.to_string())),
    }
}
```

## 五、sqlite-vec 虚拟表注册方式

```rust
/// 自动扩展注册。⚠️ 必须在 Connection::open 之前调用：
/// auto_extension 列表在新连接打开时逐个尝试加载 vec0 模块。
pub fn register_vec_extension() -> Result<(), AppError> {
    unsafe {
        let rc = rusqlite::ffi::sqlite3_auto_extension(Some(std::mem::transmute(
            sqlite_vec::sqlite3_vec_init as *const (),
        )));
        if rc != rusqlite::ffi::SQLITE_OK {
            return Err(AppError::Db(format!("sqlite-vec auto extension 注册失败 rc={rc}")));
        }
        rusqlite::ffi::sqlite3_initialize();
    }
    Ok(())
}
```

| 要点 | 说明 |
| :--- | :--- |
| 时序 | `register_vec_extension()` → `Connection::open()` → `PRAGMA key` → 迁移建 `vec0`。顺序错 → M2 报 `no such module: vec0` |
| 备选 | `load_extension` 路线需 rusqlite feature `load_extension` 且 SQLCipher bundled 构建需实测允许性——**首选 auto-extension**（零文件依赖、免 feature） |
| 验证 | 注册后连接执行 `SELECT vec_version();` 或直接建 `vec0` 表成功 |
| 回退 | `+source_text` 辅助列若不被所装版本支持 → metadata 列 `source_text TEXT` 或应用层按 rowid 回表（附录 A §A.1#5）；以 §七 隔离测试先行验证 |
| 性能 | SQLCipher + vendored OpenSSL 首次编译慢（父计划风险表）：先 `cargo fetch` 预热再 `cargo test` |

### API 实态修正（计划风险表预判情况，查证 rusqlite_migration 1.3.1 源码后适配）

1. 迁移构造用 `M::up(sql)`（无 `Migration::from_sql`）；`M::up` 只收 `&'static str` → M2 SQL 经 `Box::leak` 转 `'static`（已注释备选评估）
2. `current_version(&Connection) -> SchemaVersion`（NoneSet/Inside/Outside，`usize::from` 取值）；`to_latest(&mut Connection)` 需可变借用；无 `len()` → 本模块导出 `TARGET_VERSION` 常量
3. sqlite-vec 0.1.9 的 `sqlite3_vec_init` 是无参 C 原型，无法直接作入口——保留 transmute 但以 turbofish 显式注解（满足 clippy `missing_transmute_annotations`）

### 备份语义修正（B4.7 实测发现的真实坑）

`Connection::open` 会**创建空库文件**，原方案以 `exists()` 判断备份导致首次初始化误备空库。修正：**仅 current > 0 的前向迁移才备份**（空库无可保数据）——已写入 connection.rs 文档注释。

### 环境排障（一次性）

`cargo test` 曾卡 `target/debug/七七.exe` 拒绝访问：B1 验证时的 dev 进程链（cargo run → 七七.exe）未关闭持有 exe；中文进程名在 tasklist 乱码致漏查，经 CIM 查询定位后终止。`scripts/find-lock.ps1` 临时排障脚本已删。

### 手工验证阶段实测故障与修复（2026-10-21，提交 14daa2f）

**故障现象**：dev 冷启动 panic —— `[db] 迁移失败: ... NotADatabase(26) "file is not a database"`。

**根因**（诊断证据链，非猜测）：
1. `%APPDATA%\com.brave.qiqi\pet.db` 存在（98304B），**文件头为随机字节**（非 `SQLite format 3`）→ 库确实是加密的正常文件
2. 凭据管理器 `cmdkey /list` **查不到 qiqi 条目** → 密钥未持久化
3. 查 keyring 3.6.3 的 `Cargo.toml`：**[features] 段无 `default`** → 写 `keyring = "3"` 时**未启用任何平台后端**，于是 `Entry::new`/`set_password` 看似成功但实际不落盘
4. 后果链：每次启动生成新随机密钥 → 首次建库（K1）→ 二次启动用 K2 打开 → `NotADatabase`

**修复**：`keyring = { version = "3", features = ["windows-native"] }`。
**验证方式**：写跨进程探针（probe 专用凭据项）连续跑两次 —— 第 1 次 `CREATED:D0DC1320464414C5`、第 2 次 `EXISTING:D0DC1320464414C5`，**证明持久化成立**；随后探针凭据与临时文件已清理。

**加固**（防御同类静默故障）：
- `open_encrypted()`：open → `PRAGMA key` → `ensure_decryptable()`（读 `PRAGMA user_version` 试探）
- 不可解密时：返回**可行动的 `AppError::Config`**（明确文案），并把库**重命名隔离**为 `pet.db.corrupt-<unix秒>`——**保留证据、绝不静默删除**，下次启动自动重建
- 实测坑：隔离前必须 `drop(conn)`，否则 Windows 报 `os error 32 文件被占用`（用例 8 发现）
- 新增**用例 8** 覆盖该故障路径（换密钥打开 → Config 错误 + 隔离文件存在 + 原库已移走）

**当前现场处置**：开发期孤立库（仅种子数据，无用户数据）已隔离为 `pet.db.corrupt-1792598194`；下次 `pnpm tauri dev` 将以持久化的新密钥重建。

**对后续任务的警示（务必遵守）**：
- 引入任何"平台能力"crate 时核对 **features/default**（keyring 无默认后端是一类静默失败源）
- 涉及凭据/密钥的功能必须**跨进程验证持久化**，单进程内 set→get 通过不足为证
